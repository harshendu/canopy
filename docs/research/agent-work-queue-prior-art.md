# Durable tickets outlast every agent session

> **Prior-art survey for [`AGENT_EXECUTION.md`](../AGENT_EXECUTION.md).** Researched on
> 15 November 2026 from public documentation, specifications and engineering posts. It
> separates what was read on a primary page from what is secondary or unverified, and says
> so inline. It surveys other systems; canopy appears only in one remark of its conclusion.
> The design that draws on it — and what it takes, adapts and leaves — is in the proposal's §2.

As of November 2026 no published system runs the whole pipeline in the question: pull-based dispatch with explicit claim, retry and reconcile rules appears only in OpenAI's Symphony (a "Draft v1" spec), the best agent-to-human dialogue protocol is Linear's agent sessions, and the best separation-of-duties rules are GitHub's for the Copilot cloud agent ([Symphony SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md), [Linear](https://linear.app/developers/agent-interaction), [GitHub](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations)). None combines the three; in the ticket-driven products found, plan approval before coding is opt-in or left to the agent, no source escalates after a set number of review-and-rework cycles, and no vendor hands the agent its design documents and decisions at pickup. A delivery-management tool that owns the state store should therefore copy no single product; it should adopt their common denominator — the ticket record, never the session, carries the claim, the plan, the hand-off, the gate and the decision — and build the missing pieces itself. **Adopt** a compare-and-swap claim with a heartbeat-sized lease, a fencing token and capped attempts (the one claim the research found to behave identically on PostgreSQL, MySQL/MariaDB and SQLite), Symphony's split between dispatchable states and states parked on a human, one whole-replace plan artifact per ticket, the converged response vocabulary of approve, edit, reject and respond with no approval on expiry, and gate definitions the gated actor cannot edit, rolled out warn-before-enforce with requester-is-not-approver. **Adapt** plan-first checkpoints by making them short, risk-tiered and server-enforced, because every argument for plan review is practitioner reasoning and the only independent evidence found criticises its review burden. **Avoid** making any session-bound mechanism load-bearing: lock files, in-memory claim sets, approval callbacks held open, and on the Claude platform Stop hooks (overridden after 8 consecutive continuations), Channels and agent teams. The measured constraint is review, not generation — vendor telemetry reports 98% more merged pull requests alongside 91% longer review times, and Anthropic reports that users accept 93% of permission prompts ([Faros](https://www.faros.ai/blog/ai-productivity-paradox-report-2025), [Anthropic](https://www.anthropic.com/engineering/claude-code-auto-mode)) — so gates must be few, evidence-rich and aimed at irreversible or outward-facing actions, and ticket text must be treated as untrusted input throughout.

## Three systems each publish a third of the pipeline; none ships it whole

**How to read the evidence.** Unless labelled otherwise, a cited fact comes from a primary page — vendor documentation, a specification, a repository or the author's own engineering post — fetched for this research (state as of 15 November 2026) through a summarising fetch tool, so quoted strings are as that tool relayed them and were not re-checked against the raw pages. *Secondary* marks search snippets, third-party blogs, mirrors and community articles, often for pages never opened; *unverified* marks researcher recollection or details the fetched pages did not confirm; *vendor-reported* and *author-reported* mark measurements a party published about its own system; *inference* marks reasoning by the researchers or by this report, not a quoted source.

Published ticket-driven agents split into two families, and only one treats the tracker as a queue. **OpenAI's Symphony is the only system found in which agents pull work from tracker state**: a "Status: Draft v1 (language-agnostic)" specification whose orchestrator polls every `polling.interval_ms` (default **30000**; the Elixir reference workflow sets 5000), reconciles running work, and dispatches an issue only when it is in an active state, is not terminal, is marked `dispatchable` by the tracker adapter, carries every label in `tracker.required_labels`, is not already in the `running` map or the `claimed` set, and global and per-state slots are free, ordering candidates by `priority` 1–4, then oldest `created_at`, then `identifier` ([Symphony SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md), [reference WORKFLOW.md](https://github.com/openai/symphony/blob/main/elixir/WORKFLOW.md)). Everything else is push: a human or a rule assigns, delegates, labels or mentions, and a webhook starts a run. Linear sets the agent as `delegate` and fires a `created` AgentSessionEvent; Atlassian lets a space admin attach a "Trigger agent action" rule to a workflow transition so that "the agent is triggered when any team member moves a work item to the allocated status"; Devin starts from an assignment, a label beginning `@skills:<skill>` or an automation that fires only when a ticket "newly matches"; Cursor resolves the repository from `[repo=owner/repository]` in the description or comments, then labels, then a default; Codex runs started by Linear triage rules use the issue creator's account; Claude Code starts from the `@claude` trigger phrase, a `prompt` input on any GitHub event, or `claude --cloud`, with no native Linear or Jira trigger found on the pages fetched ([Linear agents](https://linear.app/developers/agents), [Atlassian](https://support.atlassian.com/jira-software-cloud/docs/collaborate-on-work-items-with-ai-agents/), [Devin + Linear](https://docs.devin.ai/integrations/linear), [Cursor + Linear](https://cursor.com/docs/integrations/linear), [Codex for Linear](https://learn.chatgpt.com/docs/third-party/linear), [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions), [Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)). The distinction that matters to a queue owner is level versus edge triggering (inference): Symphony re-evaluates eligibility on every tick, so a missed event costs one interval, whereas an edge-triggered automation that misses its moment never fires.

Symphony's reference workflow also publishes the fullest agent lifecycle. Its states are `Backlog` (out of scope until a human moves the issue to `Todo`), `Todo`, `In Progress`, `Human Review`, `Merging`, `Rework` and `Done`; the active list is Todo, In Progress, Merging, Rework and the terminal list is Closed, Cancelled, Canceled, Duplicate, Done ([WORKFLOW.md](https://github.com/openai/symphony/blob/main/elixir/WORKFLOW.md)). The agent itself moves a ticket from `Todo` to `In Progress` and on to `Human Review`; a human then moves it to `Merging`, where the agent lands the change through a `land` skill ("do not call `gh pr merge` directly"), or to `Rework`, a full reset that closes the pull request, removes the workpad and branches fresh from `origin/main`. **The human gate is implemented by omission**: `Human Review` is not an active state, so nothing is dispatched for it, and each tick's reconciliation stops, without cleaning up the workspace, the worker for any issue that is "active but not routable" or neither active nor terminal ([SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md)). The plan lives on the ticket as one persistent comment headed `## Codex Workpad`, opened by an environment stamp `<host>:<abs-workdir>@<short-sha>` and holding sections Plan, Acceptance Criteria, Validation, Notes and, only when needed, Confusions; the agent reuses it and never posts a second ([WORKFLOW.md](https://github.com/openai/symphony/blob/main/elixir/WORKFLOW.md)). Two cautions apply. The last ~8k characters of the spec were not read, so restart recovery and any cross-state rework limit are unconfirmed; and Symphony keeps `running`, `claimed` and `retry_attempts` in memory and re-derives everything from the tracker each tick, which makes the tracker, not Symphony, the durable store (inference).

Linear publishes the best protocol for the conversation. The human stays `assignee` while the agent is `delegate` — "humans maintain ownership while agents act on their behalf" — and the `created` webhook carries `promptContext`, a formatted string of issue details, comments and guidance, alongside structured `agentSession.issue`, `previousComments` and `guidance` ([Linear agents](https://linear.app/developers/agents), [agent interaction](https://linear.app/developers/agent-interaction)). The agent emits typed activities (`thought`, `elicitation`, `action`, `response`, `error`), and Linear, not the agent, derives the session state from the latest one: `pending`, `active`, `error`, `awaitingInput`, `complete` or `stale`. The plan is `agentSession.plan`, an array of `{content, status}` items with status `pending`, `inProgress`, `completed` or `canceled`, replaced whole on each update. Liveness is contractual: a first response within **10 seconds** or the agent is shown as unresponsive, and **30 minutes** without activity before the session is treated as `stale` ([best practices](https://linear.app/developers/agent-best-practices)).

GitHub publishes the clearest separation of duties, for a product whose new cloud experience reached paid plans on 28 October 2026. The Copilot cloud agent pushes only to a `copilot/` branch, cannot mark its pull request ready, approve it or merge it, is limited to 59 minutes in Actions-based sessions, and its pushes run no workflows until a user with write access clicks "Approve and run workflows"; the stated control "Prevents the user who asked Copilot cloud agent to create a pull request from approving it" ([risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations), [reviewing Copilot PRs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/review-copilot-prs), [about the agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). GitHub Agentic Workflows add a structural version of the same idea: the agent job is read-only and asks for writes as "safe outputs" that separate permission-controlled jobs execute under per-type caps — create-pull-request 1, add-comment 1, add-labels 5, merge-pull-request 1 (experimental) — though the page states no release stage ([gh-aw safe outputs](https://github.github.com/gh-aw/reference/safe-outputs/)).

Review and QA "by other agents" is the thinnest part of the published record. Cursor's Bugbot reviews pull requests and can spawn a cloud agent to fix its findings, capped at 3 attempts per PR when it commits to the existing branch, and GitHub's changelog of 1 September 2026 lets Copilot code review submit approvals when an admin opts in ([Bugbot](https://cursor.com/docs/bugbot), [GitHub changelog](https://github.blog/changelog/2026-09-01-copilot-code-review-can-now-approve-pull-requests)). Among open-source systems, Gas Town names roles — Mayor (coordinator), Polecats (workers), Witness (detects stuck agents), Refinery ("Per-rig merge queue processor") and Deacon (background supervisor) — and has the Refinery merge through a "Bors-style" bisecting queue so that "polecats never push directly to main" ([Gas Town README](https://github.com/steveyegge/gastown)). Cursor's own scaling report settled on planners, workers and a judge and dropped a separate integrator role that "created more bottlenecks than it solved" ([Cursor](https://cursor.com/blog/scaling-agents)); Anthropic's evaluator-optimizer pattern, in which "one LLM call generates a response while another provides evaluation and feedback in a loop", comes with advice to set stopping conditions such as a maximum number of iterations ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). The closest published match to the staged pipeline in the question is one practitioner's tool with stages `backlog -> spec -> plan -> implement -> test -> review -> done` and calls `task_claim`, `task_next`, `task_advance`, `task_approve` and `task_request_approval(task_id, stage)`, which "gates advancement, enforcing a maker-checker pattern"; its claim atomicity, lease expiry and race behaviour are not described and its adoption is unverified ([dev.to post](https://dev.to/keshrath/how-i-got-multiple-ai-coding-agents-to-stop-losing-track-of-their-work-19nb)).

## A compare-and-swap claim with a heartbeat lease is the portable queue core

The database primitives are well documented and they do not agree across engines. PostgreSQL's locking clause supports `SKIP LOCKED`, under which "any selected rows that cannot be immediately locked are skipped" — a behaviour its manual says gives "an inconsistent view of the data" yet "can be used to avoid lock contention with multiple consumers accessing a queue-like table" ([PostgreSQL SELECT](https://www.postgresql.org/docs/current/sql-select.html)). MySQL 8.0 documents the same option with the same caveat and adds that such statements "are unsafe for statement based replication" ([MySQL locking reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)); MariaDB says it "is only implemented on InnoDB tables and ignored otherwise" ([MariaDB SELECT](https://mariadb.com/kb/en/select/)); SQLite has no row locks, allows "only one simultaneous write transaction", and supports `RETURNING` only "since version 3.35.0 (2021-03-12)" with arbitrary row order ([SQLite transactions](https://www.sqlite.org/lang_transaction.html), [SQLite RETURNING](https://www.sqlite.org/lang_returning.html)). The researchers' synthesis (inference) is that **the one claim that behaves identically on all three engine families is a compare-and-swap `UPDATE` guarded by a status and lease predicate, followed by a check of the affected-row count**: `UPDATE tasks SET status='claimed', claimed_by=:w, attempt=attempt+1, lease_expires_at=:now+:ttl WHERE id=:id AND (status='pending' OR (status='claimed' AND lease_expires_at<:now))`, where one row means the claim was won and zero means pick another candidate. It needs no row lock, no `RETURNING` and no `SKIP LOCKED`. A `SKIP LOCKED` lock lasts only as long as its transaction and ties up a database connection per worker, so it suits a sub-second claim but not work lasting minutes to hours, and a worker that reaches the tool only over HTTP could not hold one anyway (inference). Three portability facts stayed unverified and need checking before a schema ships: whether MariaDB supports `UPDATE ... RETURNING`, the versions in which `SKIP LOCKED` arrived (PostgreSQL 9.5, MySQL 8.0.1 and MariaDB 10.6 are recollection), and per-engine UNIQUE-with-NULL and partial-index behaviour for a "one active claim per task" constraint.

Every mature queue pairs a lease or visibility timeout with a heartbeat or extension call, and published defaults run from 15 seconds to an hour, as the table shows. The pattern worth copying (inference from the Kubernetes 15:10:2 and Solid Queue 5:1 ratios) is a lease several times longer than the heartbeat, a heartbeat at one-third to one-fifth of the lease, and a reaper that runs at about the heartbeat cadence, which bounds recovery to the lease plus one reaper period. **Sizing the lease to the heartbeat, not to the task, is what lets an hours-long agent session be recovered within minutes of a crash**; a visibility-timeout-only design stalls for the whole timeout — Celery's Redis default is 1 hour, and work that exceeds it "will be executed again, and again in a loop", while SQS caps extension at "12 hours from when the message is first received" ([Celery Redis broker](https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/redis.html), [SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)). Beads already ships the mechanism for coding agents: a worker claims with a lease that has a TTL, keeps it alive with `bd heartbeat`, and a supervisor runs `bd reclaim`, which finds `in_progress` issues whose lease expired longer ago than `--older-than` (default 10m0s), clears the assignee, sets the status back to `open` and records a recovery event; without reclaim the issue stays `in_progress` indefinitely ([bd reclaim](https://beads.gascity.com/cli-reference/reclaim.md)). Beads' default lease TTL was not found, and its documentation's example comment conflicts with the 10-minute default. Gas Town's monitor supplies names for what a board should surface when this machinery fires: `gt feed --problems` lists GUPP Violation ("hooked work with no progress for an extended period"), Stalled and Zombie, the last being a dead tmux session ([Gas Town README](https://github.com/steveyegge/gastown)).

A lease alone is unsafe. Kleppmann's canonical failure is a client "paused for an extended period of time while holding the lock" that writes after expiry; the fix is a token that "is simply a number that increases" on each acquisition and that the storage layer checks, rejecting a write that carries 33 once it has processed 34 ([Kleppmann](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)). Applied to a database queue (inference), the claim counter is the token: increment `attempt` on every successful claim, return it to the worker, and make every heartbeat, progress write and completion `UPDATE ... WHERE id=:id AND attempt=:token AND status='claimed'`, checking the row count in the same statement and answering a superseded worker with 409 or 410. Side effects outside the database — git pushes, pull requests, tracker comments — are not fenced by the queue; branch names or commit trailers that carry the attempt number make them at least detectable (inference). For the HTTP surface Stripe and the IETF agree on the idempotency contract. Stripe "saves the status code and body of the first request made with a given idempotency key" and errors if a retry's parameters differ; the IETF's `draft-ietf-httpapi-idempotency-key-header-08` of 22 October 2026 — an active working-group draft, not yet an RFC — says a missing key on a required operation SHOULD give 400, a retry while the original is processing SHOULD give 409, and reuse with a different payload SHOULD give 422 ([Stripe](https://docs.stripe.com/api/idempotent_requests), [IETF draft](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)).

Retry policy needs a finite cap and a visible parking state. Oban's vocabulary separates waiting states (`scheduled`, `available`, `retryable`, plus `suspended`), one running state (`executing`) and three terminal states (`completed`, `cancelled`, `discarded`) ([Oban.Job](https://oban.hexdocs.pm/Oban.Job.html)); River stops at 25 attempts, while Temporal's default is unlimited. Crashes deserve different treatment from failures: Solid Queue marks jobs claimed by a pruned process as failed with `SolidQueue::Processes::ProcessPrunedError` and does not retry them automatically, because the job could be what killed the process, and Celery's `task_reject_on_worker_lost` requeues a lost task but "can cause message loops" ([Solid Queue README](https://github.com/rails/solid_queue), [Celery configuration](https://docs.celeryq.dev/en/stable/userguide/configuration.html)). For agent tasks the safe design (inference) counts every claim as an attempt, so a crash loop hits the cap, and records the end reason — lease expired versus reported failure — separately.

Field reports say contention breaks before capacity does. Anthropic's 16-agent C compiler claimed tasks by writing lock files into `current_tasks/` and letting git reject the second claimant, and it worked; Cursor's flat design, with agents coordinating through a shared locked file, did not — agents held locks too long, failed while holding them or edited without them, and "Twenty agents would slow down to the effective throughput of two or three" ([C compiler](https://www.anthropic.com/engineering/building-c-compiler), [Cursor](https://cursor.com/blog/scaling-agents)). Both accounts are author-reported. MCP Agent Mail's file reservations are advisory, with conflicts "returned alongside grants", not blocked ([Agent Mail](https://github.com/Dicklesworthstone/mcp_agent_mail)). An atomic server-side claim removes that class of failure; what remains is who computes readiness, and Beads' answer is reusable: `bd ready` lists open items with no open blockers, `blocks` and `parent-child` edges affect readiness, and `discovered-from` edges record provenance without affecting it, so an agent files follow-up work without disturbing the queue ([Beads core concepts](https://beads.gascity.com/core-concepts.md)). For waking workers the verifiable precedent is plain polling with a server-held long poll (GitLab Runner, above); push is an optimisation and the claim still has to be the compare-and-swap (inference). How GitHub, Buildkite and GitLab treat a runner that vanishes, and their manual-approval job states, could not be verified.

**Verdict.** Adopt the compare-and-swap claim, lease column, heartbeat, reaper, attempt-as-fencing-token, capped attempts ending in a parked state, and server-computed readiness. Adapt Symphony's reconcile loop and per-state concurrency caps by making its in-memory `claimed` set durable, and Temporal's three timers — schedule-to-start for work nobody picked up, heartbeat for silence, start-to-close for overrun — as three separate queue alarms. Avoid row locks held while working, a hard dependency on `RETURNING`, task-length visibility timeouts, lock files, advisory-only reservations and unlimited automatic retries.

## Hand-offs live in one plan artifact, and plan review remains unmeasured

### Continuity is carried by artifacts, not by the session

Every system that survives a session boundary does so by writing to something durable. Anthropic's long-running harness has an initializer session create `init.sh`, a progress file `claude-progress.txt`, an initial commit and a JSON feature list whose entries hold `category`, `description`, `steps[]` and `passes`; each later session runs `pwd`, reads git logs and progress files, picks the highest-priority unfinished feature, runs a basic end-to-end check, works on "one feature per session" and ends with a commit and a progress update ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). **Coding agents may change only the `passes` field**, and JSON was chosen over Markdown because the model is less likely to overwrite it inappropriately — a direct precedent for letting an agent record a verdict on an acceptance criterion while forbidding it to edit the criterion (inference). Gas Town keeps work on "hooks" described as "Git worktree-based persistent storage for agent work. Survives crashes and restarts" and gives workers "persistent identity but ephemeral sessions"; Beads records `closed_by_session` when an issue closes; Symphony resumes from the workpad ([Gas Town README](https://github.com/steveyegge/gastown), [Beads README](https://github.com/steveyegge/beads)). No source publishes a single hand-off schema; across them the record needs what was done, what is left, how to run and verify, and pointers to the branch and pull request (inference). The often-cited "landing the plane" end-of-session ritual was not found in any fetched primary page — the Beads contributor rules instead say to run quality gates, record follow-ups as issues and "Do not push to main" — so its push-is-mandatory wording stays unverified ([Beads AGENTS.md](https://github.com/gastownhall/beads/blob/main/AGENTS.md)).

### Context arrives as short standing rules plus references

Published guidance converges on a hybrid. Anthropic defines context engineering as curating "the optimal set of tokens", warns of "context rot" as recall degrades with length, and recommends just-in-time loading in which the agent holds "file paths, stored queries, web links" and sub-agents return summaries of 1,000–2,000 tokens ([Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Claude Code's guidance limits `CLAUDE.md` to what the model "couldn't work out from the code itself" — exact test commands, "Decisions that aren't in the repo", "Anything you've had to correct twice" — with the memory guide recommending "under 200" lines, and it draws the line that governs any keeper of rules: "If something has to happen every time, make it a hook, a deny rule, or a managed setting" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Scoping mechanisms differ only in syntax: AGENTS.md files nest and "the closest one takes precedence"; Kiro steering files in `.kiro/steering/` carry inclusion modes `always` (default), `fileMatch`, `manual` and `auto`; Copilot scopes `.github/instructions/**/*.instructions.md` with an `applyTo` glob ([agents.md](https://agents.md), [Kiro steering](https://kiro.dev/docs/steering/), [Copilot best results](https://docs.github.com/en/copilot/tutorials/coding-agent/get-the-best-results)). The precedence the sources imply (inference) is user prompt, then nearest directory file, then repository root, then global or organisation rules, which places an external rule store below repository files unless a tool call surfaces it. Rules pushed at an agent also misfire: Böckeler reports that an agent "sometimes over-applied constitution rules" from Spec Kit and cautions that with context files "we can never be certain of anything" ([Fowler: SDD tools](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html), [Fowler: context engineering](https://martinfowler.com/articles/exploring-gen-ai/context-engineering-coding-agents.html)).

For decisions specifically, the one source read is practitioner opinion, not a study. An O'Reilly Radar article of 2 October 2026 treats ADR status as the binding vocabulary — accepted is binding, proposed is non-binding context, superseded is historical — tells the agent on conflict to "stop and propose whether the task or the ADR should change", and reports two failure modes: agents rigidly applying an obsolete accepted ADR, and agent-edited ADRs turning into "overlitigated prose that is hard for humans to read" ([O'Reilly Radar](https://www.oreilly.com/radar/coding-agents-love-decision-records/)). Linear's `promptContext` plus `guidance` is the closest product shape to a context bundle; other agents get design material from repository files or by following links. On the Claude platform a server's instructions are cut at 4,096 characters and MCP tool output is capped at 25,000 tokens by default (`MAX_MCP_OUTPUT_TOKENS`), which forces the bundle to be references the agent pulls, not text pushed at it (inference) ([Claude Code MCP](https://code.claude.com/docs/en/mcp)).

### Plan approval is widely shipped, rarely enforced and never measured

Plan-first workflows share a lifecycle — research or spec, then design or plan, then a task list, then implementation — and keep the artifacts as Markdown in the repository: HumanLayer's `thoughts/shared/research/` and `thoughts/shared/plans/`; Spec Kit's `spec.md`, `plan.md`, `tasks.md` and `memory/constitution.md`, with a plan template that opens on "Phase -1: Pre-Implementation Gates"; Kiro's `requirements.md`, `design.md` and `tasks.md`; OpenSpec's `proposal.md`, `design.md` and `tasks.md` under `openspec/changes/<change-name>/` ([HumanLayer ACE](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md), [Spec Kit](https://github.com/github/spec-kit/blob/main/spec-driven.md), [Kiro specs](https://kiro.dev/docs/specs/), [OpenSpec](https://github.com/Fission-AI/OpenSpec)). Spec Kit frames its readiness checklists as "unit tests for English" — "No [NEEDS CLARIFICATION] markers remain", "Requirements are testable and unambiguous", "Success criteria are measurable" — the nearest published form of a definition of ready for an agent ticket (inference). The case for a human checkpoint between plan and code is HumanLayer's leverage argument — a flawed plan yields hundreds of bad lines and flawed research thousands — together with its claim that code review's main value is "mental alignment". That is practitioner reasoning. **No empirical evidence that plan review improves outcomes was found**, and the independent assessments are critical: Böckeler, writing on Martin Fowler's site on 15 October 2025, found Kiro on a small bug "like using a sledgehammer to crack a nut" (4 user stories, 16 acceptance criteria) and Spec Kit "very verbose and tedious to review", concluding "I'd rather review code than all these markdown files" ([Fowler: SDD tools](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)); a Thoughtworks Radar entry read only through a search summary (secondary) likewise faults tools that generate lengthy spec files, while its assessment of OpenSpec, also secondary, favours small "spec deltas" over full upfront specs ([Thoughtworks Radar: SDD](https://www.thoughtworks.com/radar/techniques/spec-driven-development), [Thoughtworks Radar: OpenSpec](https://www.thoughtworks.com/radar/tools/openspec)).

Where products do offer plan approval it is opt-in or client-side. Claude Code's plan mode blocks edits "until you approve the plan", offers "Yes, and use auto mode", "Yes, manually approve edits" and "No, keep planning", and saves plans to `~/.claude/plans/` unless `plansDirectory` says otherwise — a permission gate in the client, not a state on a server ([permission modes](https://code.claude.com/docs/en/permission-modes)). Claude Code agent teams approve a teammate's plan automatically, without lead review, unless the user has put that teammate into plan mode ([agent teams](https://code.claude.com/docs/en/agent-teams)); Kiro's Quick Spec variant generates all three files "without approval gates" ([Kiro specs](https://kiro.dev/docs/specs/)). The brief the agent plans against is better agreed. GitHub asks for "a clear description of the problem", "Complete acceptance criteria" and "Direction on which files need to change", and reserves broadly scoped refactors, "Sensitive and critical tasks" and ambiguous requirements for humans ([Copilot best results](https://docs.github.com/en/copilot/tutorials/coding-agent/get-the-best-results)); Devin's guide adds success criteria, validation commands and checkpoints ([Devin guide](https://docs.devin.ai/essential-guidelines/instructing-devin-effectively)); Claude Code's adds "Give Claude a check to run" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Anthropic's research-system post reaches the same list from the failure side: vague delegation duplicated work until each brief carried an objective, an output format, tool guidance and task boundaries ([multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). Completion evidence has one strong published example, Symphony's completion bar before `Human Review`: checklists complete, validation green, PR feedback resolved, PR checks green, branch pushed, PR linked and the `symphony` label present ([WORKFLOW.md](https://github.com/openai/symphony/blob/main/elixir/WORKFLOW.md)). A verdict vocabulary for a QA stage appears only in older BMAD versions, read through a package mirror (secondary): PASS, CONCERNS, FAIL and WAIVED, where WAIVED needs a reason and an approver ([BMAD qa-gate mirror](https://cdn.jsdelivr.net/npm/@ptnglobal/bmad-method@4.43.1/bmad-core/tasks/qa-gate.md)).

**Verdict.** Adopt a single, idempotently replaced plan-and-progress artifact stored on the ticket (Symphony's one workpad comment, Linear's whole-plan replace), a structured hand-off written before the claim is released, a brief built from problem, acceptance criteria, scope, verification commands and document pointers, references in place of inlined documents, and ADR status as the statement of what binds the agent. Adapt the plan checkpoint: enforce it on the server because client-side approval is skippable, keep the plan short and tied to acceptance criteria, and exempt small low-risk tickets. Avoid per-ticket spec trees, prose-only rules for anything mandatory, agent-editable criteria or ADRs, and integration keyed to command names, which have already churned — OpenSpec renamed its `/opsx:*` commands, and BMAD's current README (v6.12 stable) does not mention the story files and QA gates of earlier versions ([OpenSpec](https://github.com/Fission-AI/OpenSpec), [BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD)).

## Human gates converge on four verbs and never approve on expiry

Every human-in-the-loop system carries the same core record — a proposed action with its arguments, a human-readable description, a set of allowed responses and a correlation id to resume with — and they differ mainly in who persists it: a framework checkpointer (LangGraph, Microsoft Agent Framework, OpenAI `RunState`), the server (A2A tasks, MCP Tasks) or a durable workflow (Temporal, Step Functions task tokens). **The response vocabulary has converged on four verbs**: approve as proposed, edit then approve, reject with a reason that is fed back to the model, and a free-text respond or answer. Agent Inbox adds `ignore`, and MCP elicitation uses a separate three-way outcome in which `decline` is an explicit no and `cancel` is a dismissal without a choice. LangChain's ambient-agents post of 14 January 2025 supplies the useful typing of the request itself — Notify, Question and Review — and A2A keeps `auth-required` and `rejected` distinct from `input-required`, a precedent for keeping "needs credentials" and "agent declined" out of a generic waiting bucket ([ambient agents](https://www.langchain.com/blog/introducing-ambient-agents), [A2A specification](https://a2a-protocol.org/latest/specification/)).

What the agent frameworks leave out is who may answer and by when. Only Camunda's user task makes assignee, candidate groups, due date, follow-up date and priority first-class, and delegating or reassigning a request is not a response type in any agent framework found — it is a queue operation (inference). Gas Town shows the queue-native form: `gt escalate -s HIGH "..."` creates a tracked bead routed by severity CRITICAL (P0), HIGH (P1) or MEDIUM (P2) and acknowledged with `gt escalate ack <bead-id>` ([Gas Town README](https://github.com/steveyegge/gastown)). The framework records are also thin because the same session resumes from its own checkpoint; a tool that hands the decision to a fresh session must store the evidence snapshot and the decision in the record itself (inference).

Pausing means persisting state and returning a handle, and the published pitfalls are all about replay. LangGraph restarts an interrupted node "from its beginning", so side effects placed before the interrupt run twice. OpenAI states that "Approval permits a tool call to run but doesn't guarantee exactly-once execution" and that its SDK does "not authenticate the snapshot or the person submitting it". LangChain warns that a `when` predicate re-evaluated on resume can flip, in which case "the tool runs and the reviewer's answer is ignored, even a `reject`", that a partly invalid batch of answers can run some tools twice, and: "Don't use `respond` to deny side-effecting tools. The model treats its message as a successful tool result" ([LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts), [OpenAI HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/), [LangChain HITL](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)). The defensive recipe repeats across sources (inference): bind each answer to a request id and accept it only while that request is pending, as Temporal's cookbook does; "Ignore responses for unknown or already-satisfied keys", as MCP Tasks specifies; validate before persisting; and put idempotency keys on side effects ([MCP Tasks](https://modelcontextprotocol.io/specification/draft/basic/utilities/tasks)). MCP adds two security rules worth copying as written: servers MUST treat an echoed `requestState` as attacker-controlled, and user identity must come from the authorization `sub` claim, never from the client ([MCP MRTR](https://modelcontextprotocol.io/specification/draft/basic/patterns/mrtr), [MCP elicitation](https://modelcontextprotocol.io/specification/draft/client/elicitation)).

**No source recommends approving on expiry.** Defaults run from waiting forever (LangGraph; Claude Code's deferred call has "no timeout or retry limit") to Temporal's 5-minute example that ends in a timeout result; Cloudflare's example comments "Timeout expired - escalate or auto-reject". Escalation is otherwise built by the user from timers, and no source publishes a recommended reminder cadence beyond Cloudflare's 4-hour and 24-hour example.

The human is the weak point of every gate. Anthropic reports that users accept 93% of manual permission prompts and that "people stop paying close attention", which is why Claude Code's auto mode screens actions with a two-stage classifier and resumes prompting after 3 consecutive or 20 total blocks. The vendor-reported error rates are a 0.4% false-positive rate on real traffic (n=10,000) and a **17% false-negative rate on real overeager actions** (n=52), so a classifier thins the prompt stream but does not stand in for a human on irreversible actions ([Claude Code auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode)). Policy is layered the same way everywhere: static per-tool flags first (OpenAI `needs_approval=True`, LangChain per-tool `allowed_decisions`), deterministic predicates second, classifiers third. Practitioner blogs (secondary, figures unverified) add two usable health signals — an approval rate flattening near 100% and a flat proposal-to-approval latency of about two seconds both mean nobody is reading — and argue for batching coherent units, such as a whole change plan, over individual calls ([approval-fatigue post](https://tianpan.co/blog/2026/06/25/approval-fatigue-how-human-in-the-loop-gates-decay-into-rubber-stamps)). Audit is the least standardised part: A2A timestamps each transition and keeps `history[]`, Cloudflare's calls accept `{reason, metadata}`, OpenAI stores sticky decisions in run state, and no framework fetched records approver identity, an evidence snapshot or the difference between proposed and edited arguments by default (inference).

**Verdict.** Adopt typed requests (notify, question, review), the four response verbs with decline and cancel kept distinct, answers bound to a pending request id, an explicit expiry outcome with reminder and escalation timers, Camunda's who-and-when fields, and a decision record that captures identity from authentication, the evidence shown, any edit and the reason. Adapt Symphony's two-way routing from `Human Review` to `Merging` or `Rework` by adding a rework counter that escalates, and treat sticky approvals as scoped, logged pre-authorisations. Avoid approval on expiry, free-text answers standing in for a rejection, gate predicates that are not deterministic, callbacks held open for a human, per-action prompts for everything, and session state reported by the agent — Linear derives it from activity.

## Tracker and CI gates keep the rule out of the gated actor's hands

Trackers and CI/CD systems have run stage gates for far longer than agents have existed, and the mature ones share one structural rule: the definition of a gate sits outside the control of whoever is being gated. Azure Pipelines attaches approvals and checks to a resource — an environment, service connection, repository or agent pool — managed by the resource owner in the UI, so "Users modifying the pipeline yaml file can't modify the checks", and every check on every resource a stage uses must pass before it starts ([Azure Pipelines approvals](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals?view=azure-devops)). GitHub puts required reviewers on the environment, not the workflow, and GitLab's merge request approval policies overwrite project settings from a central policy ([GitHub environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments), [GitLab approval policies](https://docs.gitlab.com/ee/user/application_security/policies/merge_request_approval_policies.html)). **For agent-worked tickets the implication is direct: the agent must not be able to edit the gate that blocks it** (inference).

Jira offers the cleanest decomposition of a transition rule. Conditions decide whether a user can see and execute the transition; Validators check input before it happens, and if one fails "the item does not move and post functions do not run"; Post functions run afterwards. The built-in conditions include "Block transition until approval", "Previous Status Condition", "Sub-Task Blocking Condition", "Hide From User Condition" — which leaves a transition runnable only from a workflow function or REST — and "Separation of Duties condition", which blocks a user who already performed a transition on the item ([Atlassian workflows](https://support.atlassian.com/jira-cloud-administration/docs/configure-advanced-issue-workflows/)). Across systems a gate reduces to five parts (inference): an attachment point, a set of automatic criteria that must all pass, a human approval rule stating who, how many and whether the author counts, a timeout with a defined outcome, and an evidence record.

Self-approval is prevented by explicit named switches, and approvals bind to the revision that was reviewed. GitHub distinguishes the last pusher from the reviewer and dismisses stale approvals on new commits; GitLab excludes merge request authors from approving by default and separately tracks creator, committer and pipeline triggerer ([GitLab approval rules](https://docs.gitlab.com/ee/user/project/merge_requests/approvals/rules.html)); SLSA's fourth source level requires that "Changes in protected branches MUST be agreed to by two or more trusted persons prior to submission". An agent pipeline needs the same distinctions between who requested the work, which agent last pushed and who approved, and an approval on a ticket should lapse when the work product changes afterwards (inference).

Two inheritance styles recur, and one rollout ladder. GitHub rulesets have no priority — when rules conflict "the most restrictive version of the rule applies" — so lower levels add gates but never remove inherited ones, while GitLab's central policies override project settings ([GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)). GitLab documents the ladder a keeper of rules needs: in `warn` mode merge requests proceed with bot comments listing the violations, users bypass by giving a reason, and the bypass is logged as an audit event; when a rule cannot be evaluated the default is to fail closed. Open Policy Agent's decision log — `decision_id`, `path`, `input`, `result`, `bundles` with revision, `timestamp` — is the reference shape for making "what would have blocked" replayable ([OPA decision logs](https://www.openpolicyagent.org/docs/management-decision-logs)). GitHub's "Evaluate" ruleset status was not confirmed on the page fetched and stays unverified.

Outcomes and ageing are where the systems disagree. Most CI gates are binary and final for the run, and timeouts map inconsistently: an Azure approval that times out leaves the stage "marked as skipped", unapproved fork workflow runs on GitHub expire after 30 days and are marked failed, and GitLab treats approval as permission, since someone must still run the job ([GitHub fork approvals](https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-workflow-runs/approving-workflow-runs-from-public-forks)). Richer routing exists in Spinnaker's named judgment options and in Cooper's Stage-Gate outcomes Go, Kill, Hold and Recycle, the latter known here only from secondary summaries ([Stage-Gate summary](https://resources.rework.com/libraries/project-management/stage-gate-process)). The documented failure mode is the stuck approver — GitLab advises keeping required approvals below the number of users allowed to deploy — and ITIL 4's answer to approval load, again from secondary sources, is the pre-authorised standard change that skips per-instance review ([ITIL summary](https://itsm.tools/change-enablement/)). One trap is specific to agent reviewers: Bugbot's GitHub check `Cursor Bugbot` reports findings as `neutral` by default, so merely requiring the check does not block a merge ([Bugbot](https://cursor.com/docs/bugbot)). Kanban explicit policies, WIP limits on review queues and Scrum's Definition of Ready and Done were not researched; treat them as open, not absent.

**Verdict.** Adopt the five-part gate anatomy, gate definitions the gated actor cannot change, requester-is-not-approver with approvals bound to the reviewed revision, the `enforce` and `warn` ladder with audited bypass and a fail-closed default, most-restrictive-wins inheritance from workspace to team to project, and a decision log. Adapt approval-as-permission, so that an approval makes work dispatchable and never pushes it; adapt ITIL-style pre-authorisation for low-risk classes of work and gh-aw's capped safe outputs for what an agent may write. Avoid single named approvers, gates with no reject path, checks that report neutral, and any automatic move whose conflict with a manual move is undefined — the sources fetched say nothing on how Jira or Linear resolve one.

## On Claude, a gate should end the session and a new one should resume

The Claude platform offers eight places to run a worker, and three suit unattended queue work today. The documented baseline is headless `claude -p`, the CLI form of the Agent SDK, started by a scheduler or daemon the operator owns. The Agent SDK itself suits a long-lived daemon that must hold permission callbacks in process. Cloud scheduled tasks — renamed from routines and still a research preview — run each fire as a new Anthropic-hosted session, at intervals of an hour or more or on demand through an experimental API trigger ([headless](https://code.claude.com/docs/en/headless), [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview), [scheduled tasks in the cloud](https://code.claude.com/docs/en/routines)). That trigger is the only first-party way for an outside system to push-start a session: `POST https://api.anthropic.com/v1/claude_code/routines/<trig_id>/fire` with a per-task bearer token and the header `anthropic-beta: experimental-cc-routine-2026-04-01`. Its optional `text` is wrapped in `<routine-fire-payload>` and labelled untrusted, and the fired prompt is "not live user input and can't act as approval or consent for actions during the run" — so a queue should use it only to say "go and claim work" and let the session fetch the task through an authenticated tool call (inference).

Nothing in the Model Context Protocol wakes an idle unattended session. `list_changed` only refreshes the tool list; Channels do inject events into a running session, but only an interactive one on the same machine; agent teams coordinate teammates inside one interactive session through `TaskCreate`, `TaskGet`, `TaskList` and `TaskUpdate`, and are no substitute for an external queue ([Claude Code MCP](https://code.claude.com/docs/en/mcp), [channels reference](https://code.claude.com/docs/en/channels-reference), [agent teams](https://code.claude.com/docs/en/agent-teams)). For unattended workers "push" therefore means starting a new session on demand (inference).

The same logic settles how a gate should work. The platform has three human-input channels — the `AskUserQuestion` tool (1–4 questions, 2–4 options each, `header` of at most 12 characters), MCP elicitation and permission prompts — and all three are removed, denied or cancelled in unattended modes: `--permission-prompts none` removes `AskUserQuestion` and cancels any elicitation that no `Elicitation` hook answers, `dontAsk` denies it, and it is unavailable in subagents ([Agent SDK user input](https://code.claude.com/docs/en/agent-sdk/user-input), [headless](https://code.claude.com/docs/en/headless)). Two documented mechanisms let a session wait. A `PreToolUse` hook returning `defer` ends the turn so the caller can later resume the same session, but it is honoured only in `-p` mode, only when the turn made a single tool call, and only while the transcript survives the `cleanupPeriodDays` sweep (default 30 days). MCP Tasks with an `input_required` status are a public beta from v2.1.304 that `-p` does not wait for ([hooks](https://code.claude.com/docs/en/hooks), [Claude Code MCP](https://code.claude.com/docs/en/mcp)). **The robust pattern is the one 12-Factor Agents describes**: the worker calls an ordinary tool that records a request for a human, saves its state and breaks the loop; the tool's own interface collects the answer; a later trigger starts a fresh session that reads the decision from the ticket ([12-Factor Agents, factor 7](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-07-contact-humans-with-tools.md)). No platform feature has to survive the wait (inference).

A plugin carries most of the enforcement, within documented limits. Plugins ship hooks in `hooks/hooks.json`, MCP servers in `.mcp.json`, skills and agents; a `Stop` hook returning `{"decision":"block","reason":"..."}` or exit code 2 keeps the main agent from ending — until a hand-off is recorded, say — and a `SessionStart` hook with source `compact` re-injects the active claim after compaction ([plugins reference](https://code.claude.com/docs/en/plugins-reference), [hooks](https://code.claude.com/docs/en/hooks)). Four limits keep this from being a guarantee. After **eight consecutive stop-hook continuations** Claude Code overrides the block and ends the turn (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` raises the cap). `Stop` does not fire on a user interrupt or an API error, and SIGTERM runs only `SessionEnd` hooks, which cannot block. Hooks do not run under `--bare`, the mode the docs recommend for scripts. And subagents shipped inside a plugin ignore the `hooks`, `mcpServers` and `permissionMode` frontmatter fields, so separating implementer, reviewer and QA roles has to rest on `tools` and `disallowedTools`, plugin-level hooks and settings permission rules ([sub-agents](https://code.claude.com/docs/en/sub-agents)). Two further levers help: the `mcp_tool` hook type lets the tool's own MCP server act as the policy engine, and a tool forces approval on every call by setting `_meta["anthropic/requiresUserInteraction"]` to `true`, which `dontAsk` then denies outright.

Identity needs care because the 2026-07-28 MCP revision is stateless. It removes the `initialize` handshake and `Mcp-Session-Id` and tells servers that need cross-call state to "use explicit, server-minted handles passed as ordinary tool arguments" ([MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). A claim token returned by the claim call and required on every later call is therefore both the fencing token and the session's identity (inference); the docs read do not say that Claude Code sends any session identifier to HTTP MCP servers (unverified). Credentials ride in the plugin: a `userConfig` option marked `sensitive` goes to the secure credential store and is substituted as `${user_config.KEY}` into MCP server configuration ([plugins reference](https://code.claude.com/docs/en/plugins-reference)). For containment the documented stack is a container, VM or cloud environment; `--permission-mode dontAsk`, or `auto` with `--permission-prompts none`; narrow allow rules and deny rules, which "block in every mode, including `bypassPermissions`"; and managed settings. `bypassPermissions` is "Intended for isolated containers and VMs only", and the Bash sandbox is off by default and "covers only Bash, PowerShell, and Monitor commands" ([permission modes](https://code.claude.com/docs/en/permission-modes), [sandboxing](https://code.claude.com/docs/en/sandboxing)). Runaway limits exist as `--max-budget-usd`, the SDK options `maxTurns` and `maxBudgetUsd` and subagent `maxTurns`; a `--max-turns` CLI flag is named in the GitHub Actions docs and in third-party guides but was not seen on the headless reference page.

**Verdict.** Adopt `claude -p` or Agent SDK workers under a scheduler the operator owns, the tool's MCP server plus plugin-shipped hooks as the front door, a server-minted claim handle on every call, gates that end the session, and role limits built from `tools`, `disallowedTools` and plugin hooks. Adapt cloud scheduled tasks and `/fire` as an optional push-start, and `defer` with `--resume` or MCP Tasks as optional same-session resumes, always behind a server-side lease. Avoid depending on Channels or agent teams for unattended work, on plugin-agent `permissionMode`, on plugin hooks under `--bare`, on `Mcp-Session-Id` for identity, on a Stop hook as a guarantee, or on `bypassPermissions` outside a disposable container.

## Ticket text is an attack surface and review is the measured bottleneck

A ticket queue is a prompt-injection delivery channel unless it is designed not to be. Willison's "lethal trifecta" names the dangerous combination — "Access to your private data", "Exposure to untrusted content" and "The ability to externally communicate in a way that could be used to steal your data" — and advises avoiding the combination entirely, since telling a model not to obey injections is not dependable and guardrail products that claim to stop "95% of attacks" earn "very much a failing grade" ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Meta's "Agents Rule of Two" of 31 October 2025 turns that into an operating rule: within a session an agent "must satisfy no more than two" of processing untrustworthy inputs, accessing sensitive systems or private data, and changing state or communicating externally, and where all three are needed it requires "human-in-the-loop approval or another reliable means of validation" ([Meta](https://ai.meta.com/blog/practical-ai-agent-security/)). **A worker that reads ticket text, comments and linked documents while holding repository write access and network egress satisfies all three** (inference).

The documented incidents follow that path. Invariant Labs showed in May 2025 that a malicious issue in a public repository could steer an agent using the GitHub MCP server into leaking private-repository data through a pull request, located the flaw "in agent architecture, not the MCP server code", and recommended restricting an agent to one repository per session ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). Aikido's "PromptPwnd" findings, read here only through search summaries (secondary), describe untrusted issue, pull-request and commit text interpolated into the prompts of AI agents in GitHub Actions and GitLab CI that hold privileged tokens, affecting Gemini CLI, Claude Code Actions, OpenAI Codex Actions and GitHub AI Inference ([Aikido](https://aikido.dev/blog/promptpwnd-github-actions-ai-agents)). The Nx "s1ngularity" supply-chain attack of 26 August 2025 had malware invoke locally installed AI CLIs with permission-skipping flags — `--dangerously-skip-permissions`, `--yolo`, `--trust-all-tools` — to inventory sensitive files ([Socket](https://socket.dev/blog/nx-packages-compromised), [Wiz](https://wiz.io/blog/s1ngularity-supply-chain-attack)).

Published mitigations are architectural, not instructional. GitHub's for the Copilot cloud agent are a firewall that "restricts Copilot cloud agent's access to the internet", pushes confined to one branch, workflows that "are not triggered until Copilot cloud agent's code is reviewed", hidden characters filtered, HTML comments withheld from the agent, and triggering limited to users with write access ([GitHub risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations)). The Claude Code GitHub Action applies the same provenance test to the triggering actor, and Claude Code's cloud sessions keep git credentials outside the VM behind a proxy ([GitHub Actions docs](https://code.claude.com/docs/en/github-actions), [cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web)). MCP's security guidance adds rules for the tool's own server: "MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server", servers "MUST NOT treat possession of a state handle as authentication", and scopes start minimal with elevations logged ([MCP security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)). Agent identity has no standard yet: NIST's NCCoE published a concept paper in February 2026, whose PDF was not read, and the OWASP Top 10 for Agentic Applications 2026 was reached only through third-party summaries (secondary) ([NIST](https://www.nist.gov/news-events/news/2026/02/new-concept-paper-identity-and-authority-software-agents), [OWASP summary](https://cycode.com/blog/owasp-top-10-agentic-applications/)). One open question bears directly on agent reviewers: whether a Copilot code-review approval counts toward a pull request authored by the Copilot coding agent was not confirmed.

The empirical record says agents move the constraint to review. Faros found "no significant company-level correlation" between AI adoption and throughput or quality despite the per-team increases above, and a 2026 follow-up reporting a far larger jump in review time was seen only in a search summary (unverified). The academic record on acceptance is unsettled: the AIDev dataset's original paper reports agent pull requests accepted less often than human ones, later papers give per-agent rates that conflict because their filters differ, and one warns that acceptance can mask maintenance burden ([AIDev paper](https://www.alphaxiv.org/abs/2507.15003v1), [arXiv 2602.08915](https://arxiv.org/html/2602.08915)). DORA's 2025 report, read through secondary summaries, ties AI adoption to higher throughput with instability concerns and calls small batches "especially powerful" in AI-assisted settings ([DORA 2025](https://services.google.com/fh/files/misc/2025_state_of_ai_assisted_software_development.pdf)). Oversight itself degrades with exposure: in Anthropic's data experienced users auto-approve more broadly while also interrupting more often per turn (about 5% rising to about 9%), which makes a bare "human intervention rate" ambiguous. A blog claim that testers caught a planted dangerous command 13.6% of the time has no primary source located (secondary, unverified) ([scalex.dev](https://scalex.dev/blog/ai-agent-permissions-stats/)).

Metrics and runaway controls have precedents but no standards. Practitioner definitions exist for first-pass acceptance, intervention rate and rework rate, alongside the warning that a high autonomy rate "can reflect reviewers rubber-stamping" (vendor opinion, not measurement) ([Warp](https://www.warp.dev/articles/metrics-that-prove-ai-coding-agents-are-working)). Team-level aggregation that pairs speed with review time, rework and escaped defects fits both that warning and Anthropic's own practice of tracking interventions per session; no rigorous study of gaming effects on these metrics was found. For runaway control the only cited thresholds are auto mode's 3 consecutive or 20 total denials and Symphony's per-run turn cap; everything else — dollar caps, wall-clock timeouts, concurrency per issuing human — is organisation-chosen, and no source gives a cap on review-and-rework cycles.

**Verdict.** Adopt untrusted-input handling for every ticket, comment and linked document, with author provenance available to policy; per-task scoped credentials and no ambient secrets in the worker; a human gate on the state-changing or outward-facing leg; continuous integration withheld from agent pushes until a human has looked; size limits that keep batches small; and team-level metrics. Adapt the Rule of Two as the test for which stages need a human, and consecutive-denial and budget caps as runaway controls with values the team chooses. Avoid prompt instructions as an injection defence, standing "always allow" grants, acceptance rate as the measure of success, per-agent leaderboards, and the assumption that a screening classifier replaces a human on irreversible actions.

## Conclusion

The research turns the question from "which orchestrator should the tool imitate" into "which state should the tool refuse to delegate". The three things nobody ships — a stage that stays closed until a human answers inside the tool, a rework counter that escalates, and a context bundle built from the tool's own specs, decisions and document links — are all things only the system of record can provide, which makes them the tool's differentiators and not catch-up work. They also argue for keeping agent work state (claim, attempt, stage, pending request) as the tool's own overlay beside ticket status, never encoded in status names: Linear separates session state from issue status and derives it from activity, and an overlay is the only form that also works for tickets mirrored from a tracker whose status the tool must never write, as this repository's own source-of-truth rule requires.

Two cautions follow from how unsettled the ground is. Most of the Claude-side machinery a worker would lean on carries a research-preview, beta or experimental label in November 2026 — cloud scheduled tasks and their `/fire` trigger, Channels, Managed Agents, MCP Tasks, agent teams, the `agent` hook type — and names churned within the year, so the durable integration surface is a handful of HTTP and MCP verbs (claim, heartbeat, record plan, request decision, hand off) and no platform feature. And because nobody has measured whether plan review or stage gates improve outcomes, each gate is best treated as an experiment the tool can observe: start it in warn mode, log every decision with its evidence and latency, and question any gate whose approval rate sits near 100%. The verdicts above would shift most on five points left unverified: the unread tail of the Symphony spec, Beads' gate mechanics and default lease TTL, MariaDB's `UPDATE ... RETURNING` support, how CI systems treat vanished runners, and whether Claude Code identifies a session to an HTTP MCP server.
