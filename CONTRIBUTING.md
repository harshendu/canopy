# Contributing to canopy

Thanks for your interest in canopy! Bug reports, fixes, docs, tests and features are all welcome.
This guide covers how to get a working dev environment, the quality bar every change has to meet,
and the few project rules that aren't obvious from the code.

By participating you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md). Found a security
problem? Please **don't** open an issue — follow [SECURITY.md](SECURITY.md) instead.

## Ways to contribute

- **Report a bug or request a feature** with the [issue forms](https://github.com/harshendu/canopy/issues/new/choose).
  Search existing issues first.
- **Fix something.** Small, focused PRs are reviewed fastest. For anything larger — a new surface, a
  schema change, a new integration — open an issue first so we can agree on the approach before you
  invest the time.
- **Improve the docs.** If something in the README or `docs/` tripped you up, a PR that fixes it is
  very valuable.

## Development setup

Prerequisites: **Python 3.11+**, **Node.js 22+** (20.19+ works, but Node 20 is end-of-life), and
`git`. Docker is optional — handy for running PostgreSQL/MySQL locally or the full stack.

```bash
git clone https://github.com/<you>/canopy.git && cd canopy
./scripts/setup.sh          # backend venv + Python deps, frontend node_modules (idempotent)
./scripts/install-hooks.sh  # pre-commit + pre-push hooks (see "Quality gates")
python3 scripts/init.py     # interactive: writes .env with generated secrets + an admin password
```

Run the app locally (two terminals):

```bash
# backend → http://localhost:8000  (OpenAPI docs at /docs)
cd backend && . .venv/bin/activate
alembic upgrade head
uvicorn app.main:app --reload

# frontend → http://localhost:5173  (proxies /api to :8000)
cd frontend && npm run dev
```

Set `DEMO_MODE=true` in `.env` and restart the backend to get a fully populated app: sign in as the
admin, open **Demo data** (`/admin/demo`) and load a dataset. Demo connectors are served by an
offline mock, so Jira/GitHub/Drive flows work without credentials. Never enable demo mode in
production.

The background worker (Jira polling, nightly risk snapshots) needs Redis and is optional for most
work: `cd backend && arq app.workers.worker.WorkerSettings`.

Working on the Claude plugin's MCP server:

```bash
cd plugin && python3 -m venv .venv && . .venv/bin/activate
pip install -r mcp_server/requirements.txt
```

## Where things live

| Path | What |
| --- | --- |
| `backend/app/api/v1/` | FastAPI routers (REST API) |
| `backend/app/models/` · `app/schemas/` | SQLModel tables · Pydantic request/response models |
| `backend/app/services/` | Business logic — scheduling (CPM), forecasting, risk, drift, capacity… mostly pure functions |
| `backend/app/connectors/` · `app/webhooks/` | Jira / GitHub / Google Drive integrations and webhook intake |
| `backend/alembic/versions/` | Database migrations (autogenerated, reviewed) |
| `frontend/src/` | React app: `pages/`, `components/`, `api/` (typed client), `lib/` (pure, unit-tested helpers) |
| `plugin/` | Claude Code plugin: MCP server (`mcp_server/`), `skills/`, `agents/` |
| `e2e/` | Browser end-to-end tests (Selenium) |
| `docs/` | User flows, production guide, design notes |

[`CLAUDE.md`](CLAUDE.md) is the detailed architecture guide — written for AI coding agents, and just
as useful for humans. Read its *Conventions* section before touching scheduling, the
proposal/draft-plan pipelines, access control or migrations.

## Quality gates

CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) must be green before a PR can merge. It
runs:

| Area | Checks |
| --- | --- |
| Backend | `ruff check .` (strict, incl. type annotations on every `def`), `mypy app`, `pytest` on Python 3.11 / 3.12 / 3.13 |
| Migrations | `alembic upgrade head` on SQLite, PostgreSQL 16, MySQL 8.4 and MariaDB 11.4, plus `alembic check` for model ↔ migration drift |
| Frontend | `npm run lint` (ESLint, zero warnings), `npm run test` (Vitest), `npm run build` (`tsc` + Vite) |
| Plugin | the MCP server imports and registers its tools |

Run the same backend + frontend gate locally with `./scripts/ci.sh`. The git hooks from
`scripts/install-hooks.sh` run it for you: **pre-commit** checks the layers you touched, **pre-push**
runs the full gate. Please don't bypass them with `--no-verify`.

### Code standards

- **Python is fully typed.** Every function is annotated and `mypy app` must stay clean. Use Pydantic
  models from `app/schemas/` at API boundaries instead of bare dicts. SQLModel ids are `int | None`
  until flushed — narrow them before using them as `int`.
- **TypeScript is strict** — no `any`, no unused locals/parameters.
- **Keep logic pure and tested.** New aggregations, scoring and scheduling logic go in pure functions
  (`backend/app/services/`, `frontend/src/lib/`) with unit tests; components and routes stay thin.
- **Tests come with the change.** Bug fixes get a regression test; features get tests for the
  behaviour they add.
- Lint and type-checker versions are pinned (`backend/pyproject.toml`); Dependabot proposes upgrades.
  Tune rules in `pyproject.toml` / `eslint.config.js` rather than with inline ignores.

### Database changes

canopy runs on **PostgreSQL and MySQL/MariaDB in production and SQLite for local dev**, and every
migration must run forward on all three.

1. Edit the models, then generate a migration: `cd backend && alembic revision --autogenerate -m "…"`.
2. Review the generated file — autogenerate is a starting point, not the answer.
3. Follow the portability rules in [`CLAUDE.md`](CLAUDE.md) (*Three dialects must stay supported*):
   use `op.batch_alter_table` with the default `recreate="auto"`, branch enum changes per dialect,
   store naive UTC datetimes, use `Text` for long free text, and delete tasks/projects through
   `app/services/cascade.py`.
4. Run `alembic upgrade head` locally. CI repeats it on real PostgreSQL/MySQL/MariaDB; to try one
   yourself:

   ```bash
   docker run -d --name canopy-pg -p 55432:5432 \
     -e POSTGRES_USER=canopy -e POSTGRES_PASSWORD=canopy -e POSTGRES_DB=canopy postgres:16-alpine
   DATABASE_URL=postgresql+asyncpg://canopy:canopy@127.0.0.1:55432/canopy alembic upgrade head
   ```

### Project rules worth knowing

- **Keep [`docs/USER_FLOWS.md`](docs/USER_FLOWS.md) in sync.** Any change that adds, changes or
  removes something a user (or Claude) interacts with — an endpoint, page, tab, MCP tool, skill or
  subagent — updates the matching flow in the same PR, including its *Known UI gaps* / *Not built*
  notes.
- **Respect the sources of truth.** Jira owns tickets and their status: canopy syncs *from* Jira
  and never writes status back. Its only Jira write is pushing the *content* of an architect-reviewed
  draft plan. GitHub and Google Drive are read-only, except for uploading export snapshots to Drive.
- **Gate new features.** New surfaces get a feature flag in `app/services/features.py` (or are
  explicitly core) — see *Feature gates* in `CLAUDE.md`.
- **Extend the demo seed** (`backend/app/services/seed/`) when you add a feature, so demo mode and the
  e2e suite exercise it. Demo data must stay fictional.

## Pull requests

1. Fork the repo and branch from `main`.
2. Make your change with tests and docs, and run `./scripts/ci.sh`.
3. Open a PR and fill in the template: what changed, why, and how you tested it. Link the issue it
   closes.
4. Keep commits focused, with imperative messages ("Fix baseline variance on holidays").

A maintainer reviews every PR. Expect questions — they're about getting the change right, not
gatekeeping.

**AI-assisted contributions are welcome** (canopy itself is built with Claude Code). You are
responsible for what you submit: read it, run it, test it, and make sure it follows the conventions
above.
